The Wake-Up Call

SEV-1 Database Outage During a Live Client Call

Jan 28 - Feb 3
DB CPU climbed from 50% to 100% over 6 days. Zero alerts fired.
Feb 3 — 1:23 PM
DB CPU hits 100%. App starts failing. Prudential live call interrupted mid-session.
Feb 3 — 2:33 PM
Root cause identified: DB CPU saturation. No monitoring was configured on DB tier.
Feb 3 — 4:50 PM
Resolved. Capacity doubled. Alerts added retroactively.

Root Causes

  • No monitoring on the database tier — we only monitored the app
  • All environments shared resources — prod, staging, other services on same infra
  • No escalation process — capacity increase deferred instead of immediate

40+ minutes of downtime. A client call interrupted. No alerts until we looked manually. This talk is about making sure this doesn't happen again — and setting us up to scale.

DEFENSE

Protect What We Have

Observability, testing, isolation, and security.

Defense #1

Observability & Alerting

You can't fix what you can't see.

What we have

  • Sentry for error tracking — but errors are largely ignored, need to keep it clean and actionable
  • Logging — console output to PM2 rotated files, not searchable or queryable
  • PostHog for product analytics
  • Heartbeat at /monitoring/heartbeat — checks app server is alive

Gaps: No DB connectivity health check. Logs not searchable (need cloud logging). Sentry errors ignored — no triage, no on-call routing.

What we need

Infra Level

CPU/memory alerts on all servers AND databases. Thresholds at 70-80%.

App Level

DB connectivity heartbeat, request latency, cloud logging (searchable, queryable).

Voice Specific

LLM delay, STT/TTS latency, end-to-end response time per language.

On-Call & Triage

Clean up Sentry noise. Route real alerts to on-call. Make errors actionable.

Defense #3

Infrastructure Isolation

One noisy neighbor took down production.

Current state

Production backend, staging backend, People AI, and other services all share the same DigitalOcean infrastructure. One overloaded service affects everything.

This is what caused the SEV-1. Staging + prod on the same DB. Other apps competing for CPU.

Isolation plan (ordered by risk)

StepWhatWhy
1 Isolate AI Sales DB DB contention caused the SEV-1
2 Isolate AI Sales compute Separate server for the backend
3 Isolate People AI App Different usage patterns
4 Proper staging env Staging currently uses prod LiveKit — should be fully isolated
Defense #4

Security

We don't know what we don't know.

Known gaps Fix first

  • No dependency scanning — npm audit is not in our CI/CD pipeline
  • Admin panel auth — plaintext password from env vars, no audit trail
  • Outdated runtime versions — need to keep Node.js, Ubuntu, and libraries on latest stable versions

Then Systematic

  • Claude Code Security tool — automated vulnerability scanning, run regularly on codebase
  • Automated scanning in CI — npm audit on every PR, block merges on critical vulns
  • Regular penetration testing — scheduled quarterly
  • Security alerting — route findings to on-call, assign owners for remediation
OFFENSE

Move Faster, Scale Further

Deployments, containerization, multi-region, and defragmentation.

Offense #1

CI/CD Improvements

Deploying shouldn't require two people coordinating in Slack.

Current flow

CI (Integration)

  • Push code to feature branch
  • Feature-specific staging is deployed
  • Manually tested on staging
  • Manually merge to main

CD (Delivery)

  • Backend: run manual deploy script
  • Frontend: auto-deploys on push to main
  • Manually time both so changes go hand-in-hand
  • PM2 restart causes brief downtime
  • No automated rollback on failure

Target state

CI (Integration)

  • Automated checks on PR: lint, test, security scan, build
  • Preview environments per PR (automated staging)
  • Merge only after CI passes

CD (Delivery)

  • Unified pipeline: one trigger deploys frontend + backend together
  • Zero-downtime: rolling restarts or blue-green deploys
  • Auto-rollback: revert on health check failure
Offense #2

Containerization

The prerequisite for everything else.

Current state

Backend Bare Node.js + PM2
LiveKit Agent Dockerized
Qdrant Dockerized
MongoDB Managed (DO)

Why it's foundational

  • Isolation requires containers to separate services cleanly
  • Multi-region requires containers for AWS ECS / GCP Cloud Run
  • Zero-downtime deploys are trivial with containers
  • Local dev parity with production

Scope

  1. 01 Create Dockerfile for the backend (multi-stage build)
  2. 02 docker-compose for local dev (backend + MongoDB)
  3. 03 CI/CD pipeline builds and pushes images
  4. 04 Validate with staging before production cutover

Offense #4

Regional LLM & Voice Hosting

Different regions have different compliance requirements for AI providers.

The challenge

  • A Saudi client may not allow American OpenAI — needs LLM hosted in-region (e.g., OpenAI via Azure Middle East)
  • Voice providers may have regional latency differences
  • Data residency requirements vary by country
  • Currently hardcoded to specific providers — no easy way to swap per region

What we need

  • Provider abstraction layer — swap LLM/STT/TTS provider per region or per client without code changes
  • Region-aware config — map regions to allowed providers (e.g., Middle East → Azure OpenAI, APAC → direct OpenAI/Anthropic)
  • Voice provider flexibility — different TTS providers per language/region
  • Ties directly into multi-region deployment architecture

Offense #6

5,647

The problem

  • sales-voice.ts has 10+ routing paths (one per company/scenario)
  • 3 identical recruitment flows (Manulife, AXA-PH, KT-AXA)
  • 3 identical cold call flows (Prudential, generic, MSIG)
  • Merge conflicts are frequent — everyone touches the same file
  • Impossible to test prompt changes in isolation

Strategy

  • Extract shared building blocks — personality, conversation dynamics, engagement triggers (some exist but aren't consistently used)
  • Compose company-specific prompts from shared blocks
  • Enable per-company testing — change one client without risking others
  • Detailed plan exists: docs/plans/prompt-defragmentation.md
Offense #7

Background Job Reliability

30+ job types with no safety net.

Current risks

  • No retry policy — if an assessment generation job fails, it fails silently
  • No dead-letter queue — failed jobs disappear, no way to replay them
  • No frontend visibility — users don't see "processing..." or "failed" states
  • Silent failures — user never gets their feedback, never knows why

What we need

  • Retry with backoff — transient LLM failures shouldn't lose results
  • Failure alerting — know when jobs fail, route to eng team
  • Job status in UI — users see progress and can report stuck jobs
  • Dead-letter processing — replay or investigate failed jobs
Offense #8

Product Reference Accuracy

Improve how AI uses product knowledge during sessions.

Current: Static product files

  • 16 static product list files in codebase
  • Product info hardcoded in prompts
  • Assessment uses summarized product info — lossy compression means AI evaluates against incomplete data
  • Updates require code changes + deploy
  • No way to verify accuracy at scale

Target: RAG + continuous evaluation

  • RAG for product reference — dynamic retrieval instead of static files
  • Gold-standard evaluation — sampled human evaluations as benchmark
  • Continuous accuracy tracking — auto-evaluate against gold standard
  • Client-managed updates — product info changes without deploys
Offense #9

Internal Tooling

We don't have a backoffice yet. Many recurring tasks require engineer intervention.

Build a Backoffice

Currently no internal tool beyond AdminJS (eng-only). Need a proper backoffice for recurring ops tasks:

  • Whitelist emails for client admin app — currently requires engineer on-call
  • Other frequent on-call requests — automate the most common support tasks that pull engineers away from building

Automation & Tools

  • SCORM file generation — currently manual process
  • Demo builder — auto-create demos for sales team
  • Voice testing playground — pick STT provider, LLM, TTS, and voice ID from dropdowns, then run a mini-roleplay to test the setup across languages
